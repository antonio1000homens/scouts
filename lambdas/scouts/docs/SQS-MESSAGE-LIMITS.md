# Scouts invocation limits and SQS queue topology

This document replaces the older message-limit notes, which incorrectly
described `scoutsDecision` as an SQS trigger for `scouts` and referenced a test
file that does not exist.

## Queue event-source mappings

The deployed Scouts pipeline has these Lambda-managed SQS mappings:

| Queue | Consumer | Purpose |
| --- | --- | --- |
| `scoutsRequests` | `scouts2sqs` | Route enrichment, persistence and callback requests |
| `scoutsProcessing` | `sqs2scouts` | Perform enrichment and canonical event persistence |
| `scoutsProcessingDLQ` | `scouts-dlq-activity` | Record terminal DLQ activity for Operations |

`scoutsDecision` is a notification queue. It has no event-source mapping in
the repository's CloudFormation templates and must not be wired to `scouts`;
that would feed terminal decisions back into request discovery. `scoutsRequestsDLQ`
also has no Lambda consumer mapping. The deployed mappings and queue readback
are tracked in [`issue-174-s3-cost-rollout.md`](../../../docs/issue-174-s3-cost-rollout.md).

Lambda's SQS event-source mappings use AWS-managed polling. Empty receives are
therefore generated by those mappings while queues are empty; they are not a
`ReceiveMessage` loop implemented by the Scouts functions. Do not add or remove
mappings to tune polling without a tested replacement for the affected queue
consumer and its failure handling.

## `scouts` invocation limits

`scouts` is invoked through its HTTP Function URL and the scheduled EventBridge
rule. The scheduled refresh uses the `ScheduledRefreshMaxEvents` CloudFormation
parameter to bound immediate enrichment publications; zero makes the run
discovery-only while it still refreshes the agenda. Its cadence and cap are
separate settings.

For HTTP requests, a structured `{ realm: "scouts", subject: "agenda",
action: <number> }` command or `maxEvents` request parameter can set the
publication limit. Otherwise, `max_events_start` supplies the limit (default
5). The service also recognizes an explicit `_triggeredBySqs` marker and uses
`max_events_resume` (default 1), but the repository has no SQS mapping that
delivers `scoutsDecision` records to `scouts`; this marker does not establish
that such a trigger exists.

Enrichment retry and recovery are tracked by the durable stage state,
request-activity ledger, and Step Functions execution rather than the old
`runs >= 5` / `runs > 20` retry rules. Use the Activity Centre and Operations
views for current work and queue state. Queue depth is approximate and does
not identify individual requests.
